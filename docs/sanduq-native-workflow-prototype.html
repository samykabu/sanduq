in the GitHub issue.

A proposed Sanduq delivery workflow where questions from Tasks, Analyze, and later stages are visible to the team, answered in GitHub, and recorded before the agent proceeds. Designed for new projects and deliberate adoption in existing repositories.

01 / recommendation

One issue becomes the decision record

Use the feature's parent GitHub issue for team discussion. Keep its Project Status as the lifecycle phase and add a separate Decision field for visibility. Any stage that needs a material human choice publishes a structured question, pauses, and resumes only after an authorized answer is reconciled into the artifacts.

1
visible decision thread per feature

Every open question links to its stage, source artifact, options, owner, answer, and applied change. Different team members can contribute without needing the agent's VS Code session.

2
separate signals on the board

Status answers “which lifecycle phase?” Decision answers “is a team choice blocking this phase?” Neither overwrites the other.

0
unanswered choices silently accepted

Recommendations remain unchecked. The workflow pauses instead of converting an agent suggestion or a missing reply into approval.

Selected Project model. The team will answer material questions in the parent GitHub issue. Project Status retains the current workflow phase; a separate Decision field signals whether a team answer is pending. Native scheduling remains an isolated prototype; the Sanduq dispatcher owns production stage transitions.
02 / collaboration protocol

Move the question, not just the answer

Today Sanduq's GitHub clarification protocol covers the early Clarify/Brainstorm stage. The Tasks and Analyze overlays mostly hand control to upstream agent instructions, so a later ambiguity can surface as a VS Code question. The new workflow needs a stage-neutral decision service.

When a stage encounters a choice
  1. Classify it. Routine implementation details with an agreed policy can proceed; changes to requirements, architecture, scope, security, cost, or task ownership need a recorded team decision.
  2. Before using a host ask-user dialog, write a structured proposal tied to the parent issue and the current artifact fingerprint.
  3. Publish or reuse one question comment with a stable ID, such as D-42-TASKS-01. Mention the relevant people and set the Project decision signal.
  4. Persist a waiting checkpoint with the native run ID and question URL. Do not record a passed stage receipt.
  5. After a reply, reread the issue and edited comments, reconcile conflicting answers, apply the decision in the owning artifact, and post an outcome comment linking the exact change.

Unattended continuation

Discussion can be asynchronous

A scheduled runner can inspect waiting issue decisions, validate the binding reply and resume with the same credentials and pinned workflow version. A later GitHub event trigger can reduce latency, but it must treat comment text as data and reject untrusted commands. Until that runner exists, a teammate can answer in GitHub while a trusted operator performs the resume.

Host dialog rule. In managed mode, the Tasks, Analyze, Plan and Execute command overlays must direct material questions to this protocol. The prototype must test both Claude and Codex for unexpected local prompts. If an agent still asks in VS Code and proceeds on that answer alone, this collaboration requirement has failed.
03 / GitHub Project model

Selected: Status plus a separate Decision field

The answer lives in the feature's GitHub issue. The Decision field shows the blocker while Status continues to show where the workflow paused. The waiting Status model remains documented below as an alternative considered.

Selected

Option A · Separate Decision field

Keep the normal lifecycle Status: Feature Specification, Analysis, Ready, In progress, or In review. Add a single-select Decision field with None, Waiting on team, Answer under review, and Applied. Create a saved view filtered to Waiting on team.

  • Question comments remain on the feature's parent issue.
  • The issue stays in the phase where work stopped; no backward board movement is needed.
  • Multiple open questions are summarized in one field, with links in an issue summary comment or decision ledger.
  • When decisions are applied, clear the blocker and continue the same phase.

Trade-off: one more Project field and board view. A card in “Ready” can still be blocked, so the view and gate must honor both signals.

Alternative

Option B · Waiting for decision Status

Add a dedicated Waiting for decision Status column. When a stage pauses, save the previous phase as return_phase, move the card to the waiting column, and restore the exact phase after the decision is applied.

  • A single board column makes blocked work highly visible.
  • The parent issue still hosts the question and answer history.
  • Resume must use the stored prior phase; it cannot infer the return point from artifacts.
  • Project sync, Scope/Plan guards, and status ordering need an explicit pause/restore exception.

Trade-off: a waiting column mixes questions from different lifecycle phases and complicates Sanduq's current no-regress status behavior.

Disposable consumer

05 / target architecture

Separate execution, proof, and team decisions

The central adapter must make one native step equal one verified Sanduq stage. A stage-neutral GitHub decision service pauses any stage that needs a human choice. An agent CLI exit code alone cannot certify a receipt.

01 / SCHEDULER

Native Spec Kit engine

Owns step order, run ID, typed inputs, pause/resume, and command dispatch through the selected integration.

02 / CONTRACT

Sanduq stage adapter

Checks stage, issue and policy; claims once; validates the receipt; routes material questions to GitHub and reconciles retries.

03 / DOMAIN WORK

Extensions + decisions

Scope, Project, Clarify/SuperSpec, Assure, User Manual, task issues, PR logic, and a reusable GitHub decision journal.

04 / PROJECT-SELECTED GATE

CI and governance

When enabled, ci_gate.py checks selected feature and decision rules. Optional read-only reconciliation checks live answers. Branch rules, application tests, PR approval, merge and rollout remain separate controls.

Native command steps currently launch a separate agent CLI process. The prototype must verify the intended skill, exact feature/issue context and result on both Claude and Codex. A native human gate alone is insufficient: an interactive gate can prompt locally, while the required answer must come from the GitHub issue.

Preferred stage boundary

A verified stage, not a bare command

  1. Read native run ID, pinned workflow version, selected integration and structured inputs.
  2. Resolve the bound feature; reject a different issue, repository, branch, or concurrent owner.
  3. If an existing receipt is current, return success without repeating remote writes.
  4. Otherwise claim the expected stage and run its semantic command. A material question publishes to GitHub and pauses with no passed receipt.
  5. On resume, validate the binding answer, apply it to the owning artifact, and require a current receipt before reporting success.
  6. On an uncertain remote result, preserve a recoverable record; never assume a comment or issue write failed.

The spike must determine whether a custom verified step can wrap native integration dispatch cleanly. A plain command plus later shell check may resume at the check rather than rerunning the command. That is a design gap, not a production-ready solution.

Existing runtime to preserve and extend

Sanduq keeps domain authority

  • Issue-to-feature and branch binding
  • Stage-neutral decision IDs, trusted answers and an applied-decision ledger
  • Provider selection and optional processes
  • Claim token and single-owner lock
  • Evidence/input/source fingerprints
  • Native task sub-issue links
  • Assure and User Manual freshness
  • PR image and publication evidence

The native engine's requires block is advisory; Sanduq doctor and CI gates must remain active checks.

06 / state contract

Execution, evidence, and decisions must agree

Native state answers “where did execution stop?” Sanduq's feature checkpoint answers “what is still proven current?” The GitHub decision ledger answers “who chose what, based on which artifact?” None can declare completion alone.

Native run.specify/workflows/runs/<run_id>/ stores state.json, inputs.json, a workflow copy, and log.jsonl. Resume re-executes the paused or failed step; completed earlier steps are not automatically rewound.
Sanduq featurespecs/<feature>/workflow/checkpoint.json stores issue binding, selected commands, active claim, receipts, policy/dependency digests, and lineage. receipt_current checks required inputs and evidence; Verify/Review/Ready include source fingerprints.
Decision ledgerA proposed specs/<feature>/workflow/decisions.json stores stable IDs, stage, question/comment URL, answer comment URL, decision authority, source fingerprint, applied artifact and resolution revision. GitHub is the discussion surface; the committed ledger supports reproducible review.
Binding recordA proposed mapping records native run ID, feature path, issue ref, repository, branch, workflow package version, policy digest, and generation. It must be written atomically and checked on every resume. It is a pointer, not a second scheduler.
InvariantA native step may count as complete only when the matching Sanduq stage has a current passed receipt and no unresolved blocking decision. A current receipt may be reused on retry only after reconciling its external effects and exact identity.
Resume algorithm / proposed
  1. Load the pinned native workflow copy, current inputs, binding record, Sanduq checkpoint and open decision IDs.
  2. Check package/version, repository, issue, feature, branch, policy, and active-claim owner.
  3. Reread the issue thread. If a decision is still open or conflicting, stay paused; if settled, record authority and apply it once.
  4. If the stage receipt is current, return idempotent success for that exact step.
  5. If a prior stage is stale, stop and start a controlled new generation at the earliest stale stage; preserve old run history.
  6. If a claim survived process loss, inspect GitHub/PR/project effects before recovering its token.
Critical gap to prove

Completed native runs cannot simply “resume backward”

Official resume targets a paused or failed step. Sanduq may later invalidate an earlier receipt when source, policy, or documentation changes. The prototype needs a supported revalidation generation or equivalent safe rewind contract. Editing native state.json by hand is excluded.

Failure to demonstrate this is a no-go for replacing Sanduq's scheduler, even if a happy-path run works.

Partial remote write rule. A timeout or process crash after posting a clarification, creating task issues, or opening a PR is an unknown outcome. Retry first queries the remote object using stable issue/feature identifiers, reuses or repairs the existing object, and records the reconciliation. It does not issue the write twice just because the native step failed.

08 / CI gate redesign

Choose the gate at initialization

A project chooses whether Sanduq's workflow evidence gate runs, which PRs it covers, and which rule groups it evaluates. Application tests and existing CI stay project-owned. A small bug fix or other work outside Spec Kit must have a clear merge route.

Why this changes the earlier proposal. The current ci_gate.py rejects a PR without a changed specs/ feature or pr-features.json mapping. The shipped workflow template invokes it on every PR. That combination can reject an ordinary bug fix. The refactored installer must ask for gate mode and PR scope once, persist the choices in project policy, and never silently turn the gate into a repository-wide requirement.
Mode 01

Disabled

Do not install or require the Sanduq workflow-evidence job. The command remains available for an operator to run locally. Existing application CI, Assure/manual jobs and repository rules remain independent.

Mode 02 / suggested first pilot

Advisory

Run selected rules and publish a machine-readable result plus PR summary. Rule findings are visible but do not make the job a merge blocker. The wrapper distinguishes a reported finding from a verified pass.

Mode 03 / explicit opt-in

Required

Install a stable check that reports on every PR. It fails only when an applicable PR violates an enabled rule. A non-managed PR reports not_applicable and completes successfully; branch rules may require this stable check.

Initialization conversation

Ask once, then persist the answer

  1. Choose Disabled, Advisory or Required. No non-interactive install may silently choose Required.
  2. If enabled, choose managed-only (recommended) or explicitly opt into an all-PR mapping policy.
  3. Start from a lightweight or comprehensive rule preset, then toggle each rule group and show dependencies.
  4. Separately choose CI runner labels/capabilities; gate mode does not imply self-hosted infrastructure.
  5. Preview any installed workflow and required-check change before applying it. Record choices under project-owned .specify/workflow.yml.

Exception route

No dead-end PR

Non-managed work needs no waiver under managed-only scope. For an applicable feature that cannot satisfy a selected rule, permit a narrowly scoped waiver: exact feature/PR, rule, reason, expiry and approval by configured maintainers in GitHub. Validate that approval before treating the waiver as effective; a PR-authored JSON field alone is not authority. Alternatively, maintainers can change the project's gate mode or rules through a reviewed policy change. Report every waiver in the check summary.

CI placement and policy version

Keep infrastructure and evidence separate

Keep sanduq_ci.py responsible for project-selected runners and template rendering. Split the current full policy_digest = digest(policy) into versioned delivery and CI digests so a runner-only edit does not invalidate feature receipts. Migrate old checkpoints explicitly; preserve historical hashes and revalidate only stages affected by delivery-rule changes.

09 / work sequence

Five bounded prototype phases

Each phase answers a question needed by the next. The sequence avoids installing anything into a real consumer until the collaboration and recovery contracts are proven.

Phase 01

Baseline

Freeze CLI/package versions, stage and CI verdict contracts, and clean fixture. Map the selected Decision field; specify init-time gate mode, scope, rules and decision authority.

Phase 02

Dispatch

Install a small native workflow. Verify Claude and Codex invoke the intended skill once, with the right cwd and issue/feature context.

Phase 03

Decision loop

Prototype one Tasks question and one Analyze finding: publish, pause, discuss, authorize, apply and revalidate without a VS Code answer.

Phase 04

Recovery + CI

Exercise changed replies, source/target drift, concurrent claims, ordinary source-only PRs, enabled candidate-merge checks and crash-after-comment behavior using fake remotes first.

Phase 05

Adoption

Test greenfield, uninitialized brownfield and older Sanduq reset paths; verify all gate modes, runner selection, selected rules, package update/rollback and write a go/no-go record.

Prototype artifact set. Workflow YAML and package README; a stage/binding contract; disposable fixtures; test output for each integration and policy combination; recovery traces; package install/upgrade/rollback receipts; and a decision record listing any missing contract. A green unit test alone is not live integration acceptance.

11 / likely failure modes

Problems to design for before a live pilot

Double orchestration

Current Sanduq command overlays enter the dispatcher when no matching claim exists. In the fixture, use an explicit native-owner mode or isolated command registration so one agent invocation performs one stage and returns.

Two states disagree

Native marks a step complete while Sanduq has no current receipt, or Sanduq invalidates an earlier receipt after the native run finishes. A deterministic verified-stage boundary and new-generation policy must resolve both cases.

New CLI sessions alter agent behavior

Native command steps invoke Claude/Codex as subprocesses. Check credential availability, non-interactive prompts, instruction loading, context handoff, permissions, model selection, and process exit semantics. An installed integration is not proof of successful stage dispatch.

Clarification is an external event

GitHub replies are not equivalent to an immediate approve/reject gate. A wait step must preserve the posted question IDs and reread edited answers on resume, without inventing human decisions.

A host asks locally anyway

Prompt text alone may not prevent a command from invoking a VS Code or agent-specific question tool. Add an explicit managed-mode rule to every command overlay and test observable tool behavior in both supported hosts. An unavoidable local prompt is a release blocker.

GitHub conversation has competing answers

Issue comments are editable, and several collaborators may contribute. Snapshot the relevant comment IDs and revisions; require a configured decision authority; record the accepted answer and any later correction as a new decision revision rather than silently overwriting history.

Project status looks ready while blocked

The selected model requires a separate Decision field and a workflow readiness check even when Status says Ready. An optional CI decision rule adds PR-level enforcement when selected. Inspect Project automations and create a waiting-decisions view so teammates do not miss a blocker.

Gate mode or applicability is unclear

A required check that runs on every PR can block an ordinary bug fix if “no feature” is treated as failure. Managed-only scope must return a clearly labeled successful not_applicable result for such PRs. Advisory findings must remain visible without blocking merge; Disabled must leave no stale required check behind.

Evidence gate passes the wrong candidate

The current template checks the PR head. A target branch may advance before merge. If Candidate merge is selected, check the exact merge SHA and fail on stale evidence; if unselected, report that this freshness check was not performed.

CI policy edit invalidates unrelated work

The current checkpoint hashes the full policy, including runner choice. The proposed digest split needs a versioned migration so runner changes do not force feature work to be redone, while delivery-rule changes still invalidate the right receipts.

Optional and provider paths diverge

QA/manual selection and core/SuperSpec provider choices come from Sanduq policy and installed compatibility. A native branch must preserve the selected one, not silently choose a different command when a package changes.

Distribution is not atomic by default

Native workflow packages can carry scripts, while bundles can compose extensions, presets, steps and workflows. Test refresh and rollback explicitly; do not assume a bundle upgrade restores every modified component after failure.

12 / installation paths

New project, existing code, or older Sanduq

Canonical workflow source stays in Sanduq. Each consumer retains its own GitHub Project mapping, decision authority, CI runners, QA/manual choices, specs, evidence and constitution. The installer should detect the starting state and show a reviewable plan before writing.

Path A / new project

Start clean

  1. Initialize a repository with a selected Spec Kit integration.
  2. Install the versioned Sanduq bundle or its pinned extension, preset and workflow components.
  3. Configure GitHub repository/Project identity, the separate Decision field and waiting view, decision authority, QA/manual choice, CI gate mode/scope/rules and runner policy.
  4. Run doctor and a disposable issue walkthrough that includes an ordinary non-feature PR before real feature work.

The future bundle is a distribution convenience, not a substitute for explicit project policy.

Path B / brownfield, no Spec Kit

Initialize in place

  1. Commit or stash work and create a reviewable adoption branch.
  2. Run specify init --here --force --integration <key>; review the generated diff.
  3. Capture the repository's real architecture, CI and compatibility rules in the constitution.
  4. Install Sanduq; select Project board policy and CI gate choices; preserve existing CI/custom files and inspect required checks.
  5. Start with one bounded new issue. Do not retroactively manufacture specs for the whole product.

Official existing-project guidance ↗ supports this in-place baseline.

Path C / older Sanduq

Prefer a clean managed reset when safe

  1. Inventory active claims, feature checkpoints, specs/, constitution, project policy, CI, manuals, required checks and generated agent registrations.
  2. Back up and compare the managed install on a separate branch or worktree.
  3. If no active feature or unique customization depends on the old install, remove/recreate replaceable managed components through supported CLI paths, then initialize and install the new package with explicit gate choices.
  4. Restore retained project data and run doctor, command resolution, ordinary-PR and clean-checkout checks.
  5. If features are active, finish or explicitly archive them on the old version; start new issues on the new workflow. Migrate a live checkpoint only with a tested mapping.
Reset boundary. A whole-directory delete of .specify/ is not the default reset. It can contain the constitution, customized templates, workflow policy, checkpoints and other shared project material; specs/, User Manual and CI can also depend on it. Deleting only proven replaceable installation outputs after a backup may be quicker for an unused old setup. The installer should refuse a destructive reset when active claims or unmapped custom data are present.
Package contract. Use the unique workflow ID sanduq-delivery, pin tested CLI and Sanduq component versions, package deterministic helpers with the workflow, and preserve project-owned configuration. Official workflow packages carry companion scripts; bundles can compose extensions, presets, steps and workflows, but their update/rollback behavior still needs explicit testing. Issue-bound branch and folder names may derive XXXX-github-issue-title from the verified issue snapshot. A separately selected non-issue route can retain Spec Kit numbering. Adoption must not rename an already active feature.

13 / release decision

Release only when collaboration is real

Go to a controlled new-project pilot only if

  • Tasks and Analyze route material choices to the GitHub issue without relying on a local VS Code answer.
  • Open, conflicting, edited and applied decisions have stable IDs and correct authority checks.
  • The selected Decision field blocks workflow readiness while Project Status retains the right phase.
  • One native step equals one current Sanduq receipt; drift and partial writes recover safely.
  • Init captures Disabled/Advisory/Required, scope and rule choices; ordinary non-feature PRs merge under managed-only scope.
  • Enabled CI rules report exact coverage and limitations; product tests and review remain separate.
  • New, brownfield and old-install paths preserve project-owned data and pass supported package tests.

Do not release if

  • An agent can complete a stage after asking or receiving an unrecorded local answer.
  • Native steps can complete without a current receipt or cannot safely resume earlier stale work.
  • One teammate's non-authoritative reply or a bot recommendation becomes binding silently.
  • A retry duplicates comments, sub-issues or PRs.
  • An ordinary non-feature PR fails solely because it has no Spec Kit feature.
  • A disabled gate leaves a stale required branch check, or an unselected rule is presented as passed.
  • Resetting an old installation would discard active or unmapped data.

If native scheduling does not pass, keep the new GitHub decision protocol as a Sanduq extension and use the existing dispatcher. The collaboration goal does not depend on adopting the native engine.
