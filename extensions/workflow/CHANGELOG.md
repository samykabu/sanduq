## [2.3.0] - 2026-11-04

- `profiles.minimum_tier` can keep a narrow feature on the standard or full profile without changing its verified effort score. The default remains lite. An existing feature keeps its frozen tier; selected QA, manuals and final review remain part of the standard profile.
- The existing toolchain digest includes installed package inventory members, static JSON and project-managed delegate sources, including executed Windows PowerShell helpers when no package inventory exists. Malformed or escaping inventory entries refuse with `PACKAGE_INVENTORY_INVALID`. Mutable project state and globally linked tools remain outside this package-content boundary.
- Managed QA, manual, PR and progress instructions reuse the existing immutable evidence snapshot and its facts instead of copying inventories into each narrative. Receipt, freshness and publication requirements remain intact.
- Keep a validated toolchain fixed during a feature. Resolve an active claim and use the supported upgrade and reviewed migration for a documented blocker or security correction; do not edit checkpoint state or replace a frozen profile by hand.
- Bundles the released agent-tools 1.9.1 delegate driver: structured token counters retain their original numeric text while secret values remain redacted. Both host marketplaces pin that release; the Progress vendor source bytes are unchanged.
- Native routing evaluates each configured candidate independently and prefers eligible local native tiers, preserving a promoted fallback's configured choice. High, light and documentation tiers have distinct pinned roles alongside the existing worker and reviewer; model-only candidates do not guess a role from a shared model name. A pinned role must support the actual work type: implementation/high remains external with `native-unsupported:role-work-type`, without changing its configured tier or model.
- Selected native stage and task-card handoffs refuse missing, custom or wrong-model role files with `ROLE_FILES_STALE`. Custom and linked role files are retained, and generated role files participate in the existing install rollback. Collector authoring boundaries and native-review safety/lineage checks remain intact.

## [2.2.3] - 2026-10-31

- Scope `export-plan` validates the affected dependency graph before its first write and refuses, writing nothing remote or local, on a cancelled (not planned) prerequisite (`SCOPE_EXPORT_CANCELLED`), a missing target (`SCOPE_EXPORT_MISSING`), work depending on an aggregate (`SCOPE_EXPORT_AGGREGATE`), an aggregate without approval (`SCOPE_EXPORT_UNAPPROVED`) or a dependency or sub-issue cycle (`SCOPE_EXPORT_CYCLE`, shown as `#a -> #b -> #a`); each error names the links to remove or correct (#115). Before, the issue bodies and local catalog were written first and a cycle was only recorded afterwards.
- Cancelled issues are never written by export or by a split publish's rewire.
- The export journal records exact before-images before the first write: issue bodies, the Project `Blocks` values, the native blocked-by links and the planned writes; rewire saves native links separately from declared ones. `cancel plan-export-<n>` accepts a standalone export, marks it rolled back and prints the before-images; like `cancel` for a publish it does not write to GitHub.
- Clearing a Project text field sends `--clear` on the command-line route instead of an empty `--text`.

## [2.2.2] - 2026-10-31

- Publishing a declared dependency that Git ignored at completion (`git add -f`) with unchanged bytes no longer makes Verify or Review stale: source drift compares a path the inventory lacks against the receipt's own fingerprint for it (#109). Changed bytes, deletions and undeclared ignored files still drift.
- `revalidate-upstream` can start at Scope (`--through scope`). It re-stamps a stage whose recorded hash still equals the attribute-free text reading of the current bytes, such as after a later `specs/** -text` rule, keeping every receipt with a `revalidated_upstream` audit record (#111). A real Scope change is refused with `REVALIDATE_UPSTREAM_SCOPE_NEEDS_CLAIM`; before, later stages were re-recorded while Scope stayed stale.
- A missing, truncated or tampered source-inventory side file fails the CI gate as `SOURCE_INVENTORY_INVALID` (naming the file and its recorded and found sha256) instead of `STALE_RECEIPT` with every source path listed, and the recovery advice is to restore the file from Git, not to re-record the stage (#114). This code cannot be waived, as `check_index` already treated it.
- A decision question with line breaks round-trips: the title parser spans lines, and `ask` reads back the rendered comment before posting, refusing one that would not parse back with `DECISION_QUESTION_INVALID` and no comment or ledger entry (#116).
- Another feature's untracked files under `specs/<other>/` are no longer implicit QA or manual inputs (#113, shared `sanduq_freshness.py`). Pins Assure 2.7.3 and User Manual 2.0.2.

## [2.1.0] - 2026-10-30

- Receipt log. Every checkpoint save appends one line per receipt it changed or removed to `specs/<feature>/workflow/receipt-log.jsonl`: the stage, the SHA-256 of the receipt's JSON with sorted keys (`null` when removed), the time and `by: dispatcher`. A save that finds a receipt on disk that differs from its newest line logs it as `by: outside-edit` before writing, so a hand edit is never adopted silently. The CI gate (receipts rule) refuses a receipt whose newest line is not the dispatcher's hash of it with the new registered `RECEIPT_EDITED_OUTSIDE_DISPATCHER`, a PR that changes or drops lines already merged on the base branch with `RECEIPT_LOG_REWRITTEN`, a deleted log with `RECEIPT_LOG_MISSING`, and a damaged line with `RECEIPT_LOG_INVALID`; all four are waivable under `receipts`. A stage edited by hand and then re-recorded passes with `RECEIPT_OUTSIDE_EDIT_SUPERSEDED`. The gate result lists the entries the PR added as `receipt_log.added`, and the pre-publish index check requires the log next to the checkpoint. A feature started before 2.1.0 passes with `RECEIPT_LOG_ABSENT` until its next save starts the log. Limit: the log lives in the same checkout, so someone who also writes a matching line by hand gets through; review sees every added line.
- Depends on User Manual 1.9.0 (Arabic PDFs in Amiri, right-to-left kept in PDFs, PDFs for themes other than Material and MkDocs).

## [2.0.4] - 2026-10-29

- A native-first stage's claim prints the exact `delegate_dispatch.py attest-native --feature <feature> --id stage:<stage> --claim-token <token> --requested-model <model>` command as `cli.record_native`, ahead of `cli.complete`. In the native and external routing live runs, 6 of 7 refused completions were `DELEGATION_STAGE_NOT_VERIFIED` on Scope or Clarify: the host ran `complete` for a stage a native subagent did before recording the native attempt. On a native-first route, `DELEGATION_STAGE_NOT_VERIFIED` now opens with that same filled-in command; on an external route it still says to collect, accept or reassign first, and its attest-native command carries the claim token instead of `<token>`. The lite card and the routing rule say to record the native attempt with `attest-native` or `record-native` before `complete`.
- `ACTIVE_STAGE_MUST_BE_RESOLVED` no longer offers `pause`, which keeps the claim active and so never resolves it. The registry remedy and the install, upgrade and host-switch blockers say to complete the stage or release the claim with `workflow.py recover --feature <feature> --token <token> --reason "<why>"`, adding `--force-live-owner "<this session releases its own claim>"` when this session owns it. Host-switch blockers now print that command too.
- The shared helpers packaged into `scripts/` and the `sanduq_hash.py` and `sanduq_ci.py` modules other packages ship start with an `SPDX-License-Identifier: MIT` line; dependency pins follow the patch releases of Project, PR, Assure and User Manual. No behaviour change. (2.0.3 is reserved for a parallel release.)
- `references/execution-assign.md` marks the cache-read share of a worker's tokens and the saving from reusing a reviewer as estimated. No behaviour change.
- Scope's fresh read gate (`scope.py gate`/`bind` with `--feature --token --session`) accepts a child kept whole whose keep-whole revision carried its parent's approval. Since 1.21.0 `publish` records such a child's receipt with the revision's own analysis hash, `child_count` 0, `carried_forward` and `revision_of`, while the gate still demanded the parent's approval verbatim, so every carried child failed `SCOPE_RETAINED_PARENT_APPROVAL_MISMATCH`. The gate now follows the receipt's lineage through this issue's local approval records (`.specify/scope/approvals/<issue>-<hash>.json`, which `approve` and `publish` write): the receipt must equal the newest record, each hop is a carried leaf of this issue and repository with the same approver and time, and `revision_of` must lead, without a cycle, to the live native parent's current approval, whose local owner record still matches it. A forged, missing, cyclic, foreign-issue or broken link, a different parent, or a parent approval changed since still fails with the same code. A project stuck on this refusal re-runs the same `gate` command after upgrading; nothing is re-approved or migrated, provided the records `publish` wrote are still in that checkout.
- The same gate refuses, with the new registered `SCOPE_CARRIED_APPROVAL_WITHOUT_PARENT`, an issue that has no native parent but whose receipt approval was carried forward from another issue's approval, as happens when a child kept whole and revised is later unlinked from its parent: that approval covered it only as the parent's child. So that any checkout can tell whose approval a receipt carries, `approve` (and a keep-together policy settlement) records `approval_origin` (the `issue` and `analysis_sha256` of that explicit approval), each carried revision copies it unchanged, and `publish` writes it into the receipt. Without a native parent, a carried approval passes only when it originates in this issue: with this checkout's approval records, `revision_of`, followed through this issue's records, must lead to an approval recorded for this issue itself and the receipt's `approval_origin` must name that approval, so a receipt edited to claim its own origin is refused; without the records, the receipt's `approval_origin.issue` must be this issue. A receipt published before 2.0.4 has no `approval_origin`; without the records it passes only when the issue body carries no `speckit-scope:node` marker from another issue's publish. A root kept whole and revised, and a former child approved and published as its own root and then revised (its body keeps the former parent's node marker), keep passing with or without the records. A refused issue is re-scoped and approved as its own root.

- Vendors agent-tools 1.8.2: on Windows, delegate-task runs the harness inside a job object that ends every harness descendant when the supervisor exits, a hard kill included; results carry `process_containment` (`mechanism`, `closure`). Each Windows harness launch starts about 1 to 2 s later; the lost-run containment lookup keeps the bounded journal read.

## [2.0.2] - 2026-10-28

- Routes are fixed for a claim. Every claim records `delegation_digest`, the digest of the normalised `delegation` policy section `selected_route` reads, on `state.active`. `delegate_dispatch.py start` (and every external launch: retry, reassign, confirmed fallback), `record-native`, `adopt` (`accept --no-attempt`) and `attest-native` refuse with `DELEGATION_POLICY_CHANGED_IN_CLAIM` (new registry code) when the current section differs: restore `.specify/workflow.yml` to finish the claim on its recorded routes, or, to adopt the new policy, release the claim with `workflow.py recover --feature <feature> --token <token> --reason "<why>"` and claim again (`pause` keeps the claim, so a new claim would refuse with `STAGE_ALREADY_ACTIVE`). A live lite run had edited a task's override mid-claim after `record-native` refused its external route, turning it native without a trace. A claim recorded before 2.0.2 has no digest and is not checked.
- Each attempt those commands record carries the claim's `delegation_digest` and `delegation_claim_id`, and a task attempt the Execute claim's `execute_claim_id`. The Execute receipt keeps the claim's digest, and Ready refuses a task attempt of that claim, or one that names no owning claim, recorded under another digest (`DELEGATION_POLICY_CHANGED_IN_CLAIM: T###`), so a ledger written any other way is caught too. A task adopted or recorded during a later claim was checked against that claim's digest and is not compared again, so a policy changed between claims does not fail Ready. Attempts and receipts without a digest are not compared.
- `NATIVE_ROUTE_DISALLOWED` no longer suggests editing `delegation.native_allowed`: its next step is `delegate_dispatch.py start --feature <feature> --id <id>`, and changing a route is an owner decision made between claims. The fallback-confirmation and provider-rejection messages that name a policy edit now say to release the claim with `workflow.py recover`, edit, and claim again.
- Task annotations in `tasks.md` add `route_kind` and `route_reason`, so the coordinator sees whether the host may run a task before assigning it.
- The routing rule says it in one sentence: routes are fixed for the claim; never edit `.specify/workflow.yml` during a claim.

## [2.0.1] - 2026-10-28

- `adopt` (`accept --no-attempt`) refuses a task whose selected route is external, computed as `record-native` computes it, with `DELEGATION_ADOPT_ROUTE_EXTERNAL` (new registry code) naming `delegate_dispatch.py start --feature <feature> --id <T###>`. A live lite run had implemented every externally routed task in-session and adopted it, which substituted the route silently. `--reason "<why external could not run>"` still adopts and records the attempt's `route_reason` as `external-substituted:<reason>`; adopt's output carries a `warning` and Ready warns with `DELEGATION_TASK_SUBSTITUTED`. With delegation off, a native-first route or review work (under an interim security rule), adopt behaves as before. Light-tier `[Collect]` tasks are external by default (no role file pins the light tier), so adopting one with delegation on now needs `start` or `--reason`.
- Every adopted attempt records `route_kind: in-session` and `route_reason` (`adopted` or the substitution), and adopt's output prints both. `accept --run-id` refuses `--reason` (`DELEGATION_ACCEPT_REASON_NO_ATTEMPT_ONLY`). The fallback-confirmation message's "run natively" adopt command passes a `--reason`.
- The lite card, the lean Execute fragment, the routing rule and the adopt section of the delegated-workers reference say it in one line: a task routed externally runs with `start`, `collect`, `accept`; never implement it in-session and `adopt` it.

## [2.0.0] - 2026-10-28

Breaking: Scope is part of Workflow, and every Scope command is renamed. Spec Kit 1.1.3 refuses an extension command whose name does not start with `speckit.<extension id>.` (`Command 'speckit.scope.run' must use extension namespace 'workflow'`), so `speckit.scope.<x>` is now `speckit.workflow.scope-<x>`: `scope-run` and `scope-plan` are host commands; `scope-guard`, `scope-bind`, `scope-after-specify`, `scope-plan-guard` and `scope-reconcile` are Workflow's hooks, found by the event dispatcher by file name and never host skills. The skill names `scope-analyst` and `github-clarification` are unchanged (Spec Kit renders skills only from commands, so it does not namespace them).

- Scope's scripts are in `scripts/scope/` (`scope.py`, `clarification.py`, `accept_plan.py`, `workflow_policy.py`) and import Workflow's `workflow.py` and `decisions.py` directly instead of loading them by path; `sanduq_scope_github.py` is in `scripts/` and `decisions.py` imports it. Scope's skills, `references/` and `examples/` are in this package at the same relative paths, its tests run in this suite (`tests/test_scope*.py`), and the `scope-gate` and `scope-brainstorm` presets ship only here. Error codes and messages are unchanged apart from the command names they print.
- `dependencies.json` no longer pins `scope`, and `doctor` no longer needs it. Scope's state stays in `.specify/scope/` and is read in place; the issue-body markers (`speckit-scope:metadata` and the others) are unchanged.
- The installer runs `specify extension remove scope` for an installed Sanduq Scope (1.x, or the retired 2.0.0 shim) before any other package change, inside its rollback transaction, and reports it as `scope_removed`; another source's `scope` stops it with `EXISTING_EXTENSION_SOURCE_CONFLICT: scope`. Spec Kit never enforces `requires.extensions`, so this order is the installer's. An upgrade, or a Scope removal, re-adds the presets, because the workflow preset now replaces `speckit.workflow.scope-run`.
- `doctor` fails with `SCOPE_MERGED_INTO_WORKFLOW` (new registry code) while a Scope before 2.0.0 is installed, naming the `upgrade.py` command; it still fails with `DEPENDENCY_SOURCE_MISMATCH` when an installed `scope` or `memory` is not Sanduq's.
- `migrate` treats a checkpoint's recorded `speckit.scope.run` as `speckit.workflow.scope-run`: the rename invalidates no receipt, and the migrated checkpoint records the new name.
- `release.py prepare` copies `deprecated` and `superseded_by` from a manifest's extension block into its catalog entry.
- `upgrade.py` without `--apply` now runs the checks apply refuses on and lists them in `blockers`: each feature with an active claim (`ACTIVE_STAGE_MUST_BE_RESOLVED: specs/<feature>; ...` with its exact `recover` command, which install and apply now print too) and a locally edited gate workflow (`CI_WORKFLOW_HAS_LOCAL_EDITS`, naming `--preserve-ci`). A preview no longer reports clean when apply would fail. Nothing is written.
- `upgrade.py` reuses the `--preserve-ci` choice the last install recorded (`install-lock.json` `preserved_ci`, else the receipt) and says so (`preserve_ci_reused`, and a stderr line); `--preserve-ci` or the new `--no-preserve-ci` still wins. `CI_WORKFLOW_HAS_LOCAL_EDITS` is a registry code with `explain` and a next step.
- Install, upgrade and host-switch rollback snapshots include `.specify/integrations/`, so the `<host>.manifest.json` files Spec Kit rewrites during `specify extension add`, `preset add` and `integration use` come back byte-identical after a rolled-back attempt.
- `claim`'s `confirm_invalidation` result adds `invalidation`: every receipt the claim would remove, the claimed stage's own included, with `completed_at` and why: `stale: <reason>` and its changed `paths` (or `rule`, `lanes`, `detail`), `current; removed only because it follows <stage>`, or `policy-changed`. It is computed before anything is written (#112).
- Retain-on-unused-claim: a claim keeps the receipts it removes in `active.retained` with a digest of the source inventory and every recorded dependency, and a confirmed claim prints them as `invalidated`. `recover` restores them unchanged when the claim did no work, decided only from state the runtime wrote: no delegated or native ledger attempt bound to the claim, the same policy and the same digest (a rejected completion that changed no file leaves nothing to undo). A restored receipt is re-evaluated, so a stale one stays stale and is never reported missing; otherwise they stay as history in `recoveries[].claim.retained`. `recover` and `recoveries[]` report `retained` (`restored`, or `kept_as_history` with `because`) (#109, #112, #114).
- `delegate_dispatch.py accept --no-attempt --id <T###> --command "<check>" --expect counts|files [--owned <path>] --nonce <n>` adopts a checked task that has no attempt. `adopt` stays as an alias with the same arguments and byte-identical output; both run one implementation. `accept` without `--no-attempt` still needs `--run-id`, and mixing the two modes is a usage error (exit 2). No behaviour changes.
- The parse_counts and light-tier summary path and the ledger trust markers are documented as advisory. No migration was removed: each one reads state a released version can have left.
- CONTRIBUTING.md adds the no-behaviour-change rule for cleanup pull requests.
- Script comments and docstrings state the rule they protect instead of citing review rounds, finding numbers or reviewer ids; `check_docs.py` refuses such a citation in `extensions/*/scripts` and a round- or review-named test module. Test modules renamed by behaviour: `test_scope_round4` is `test_scope_identity_listing_reconcile`, `test_scope_round5` is `test_scope_cancel_transport`, `test_execution_protocol_b11` is `test_execution_protocol_references`. Reference-text tests check headings, commands, codes and key terms instead of pinning sentences. `worker_brief.py --help` drops two finding citations; no other output changes.

### Migration

- Run `upgrade.py --version 2.0.0 --apply`, then `workflow.py migrate --feature specs/<feature> --reason "Scope merged into Workflow"` for each feature in progress. The old-to-new table is in docs/start/upgrades.md.
- Replace `/speckit-scope-run`, `/speckit-scope-plan` and `.specify/extensions/scope/...` paths in your own notes or scripts.
